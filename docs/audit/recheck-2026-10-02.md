## OF-001 — стан runner та епілог

[AutomationRunner:92](../../Sources/TwinCAT.OpenFramework.Automation/AutomationRunner/AutomationRunner.TcPOU#L92), :101, :110 тепер використовують `JMP FINAL_ACTIONS`. Label розміщено після state machine на :128; далі cleanup exceptions/memory, CycleCounter++ та CodeExecutionPhase=false. Присвоєння RUNNING на :118 більше не досягається після null/INVALID component.

Перевірені статичні шляхи: null перший/останній; INVALID до/після pending component; усі initialized; хоча б один pending; guard empty components; SystemDataValid=false. На invalid paths State та ErrorMessage зберігаються, на all-ready — RUNNING, на pending — INITIALIZING. Guard із недостатньою кількістю components також більше не пропускає епілог.

Це усуває OF-001. Епілог не став гарантованим для довільного exception, який виходить за межі component.Initialize/Execute або cleanup; це інший обсяг, не причина залишати OF-001 відкритим. Коректність JMP/label у реальному compiler ще не перевірялася.

## OF-004 — відділення resource ownership від queue execution

Повторно прочитано Task.Cancel/Execute/handleRunning/ResourceManager/OnStopped, повний TaskQueue та StandardTaskQueue, ITask/IResourceManager, FileContentManager.Enqueue/ResourceManager, FileContentTask і наявні TaskSequenceTest/FileContentManagerTest. У Tasks sources немає змін щодо baseline.

У типовому **FileContentManager → FileContentTask** handle належить manager-черзі. Child отримує borrowed FileHandleResource, але не власний ResourceManager. Після Cancel самої FileContentManager черги її Task.handleRunning продовжує RESOURCE_RELEASING та викликає власний ReleaseResource. Початковий OF-004 не можна застосовувати до цього сценарію як доказ незакритого файла через непомпування child.

Залишається інший шлях: **StandardTaskQueue → child із власним ResourceManager**, наприклад вкладена FileContentManager, якщо таке використання дозволене контрактом. StandardTaskQueue.Enqueue приймає ITask без перевірки ResourceManager. За child.State=RUNNING, child.ResourceAcquired=true і child substate=PROCESSING:

1. Parent.Cancel викликає TaskQueue.OnBeforeStop → child.Cancel.
2. Child.Cancel переводить child до RESOURCE_RELEASING; у цьому processing path не викликає ReleaseResource одразу.
3. Parent.ResourceManager не перевизначено, тому parent переходить у STOPPED.
4. Наступні parent.Execute викликають порожній OnStopped; child.Execute більше не викликається через OnRunning.

Якщо ніхто окремо не виконує child.Execute, його release не просувається. Це статично простежений умовний сценарій, але він не відтворений у runtime і не підтверджений як підтриманий спосіб використання власником. У поточних переглянутих tests StandardTaskQueue використовується з CounterTask без власних resources, а FileContentManager виконується окремо.

Потрібний контракт: чи queue гарантує завершення cleanup будь-якої ITask, яку приймає, чи child із власним асинхронним resource заборонений/виконується додатковим scheduler. За другого варіанта знахідку слід перекласифікувати в обмеження або вимогу документації. Не оголошую її безумовною помилкою всіх черг.

## OF-005 — TurnOff

[IntersectionController:327](../../Sources/TwinCAT.OpenFramework.Samples/Intersection/IntersectionController/IntersectionController.TcPOU#L327) тепер використовує `_TurnOffButton.Changed AND_THEN _TurnOffButton.Value`. Condition більше не залежить від TurnOn.Value. Для натискання off за TurnOn=false виконується TurnOff; для відпускання off (Value=false) гілка не спрацьовує. Вищі ELSIF-гілки зберігають попередній пріоритет. Первинний дефект усунутий без зміни контракту IO processing.

## OF-006 — close failure та завершення task

[FileHandleResourceManager.ReleaseResource:210](../../Sources/TwinCAT.OpenFramework.FileSystem/Tasks/File/FileContent/FileHandleResourceManager.TcPOU#L210) тепер повертається без close, якщо handle не acquired. За acquired handle викликає close і чекає `NOT bBusy`; лише тоді скидає flag і reset open. На :223 є перевірка bError: error path логує ERROR, success path — «closed». Отже, первинне твердження «close error ігнорується та журналюється як успішне закриття» більше не відповідає коду.

Водночас `_FileHandleAcquired := FALSE` виконується перед bError check, і error path лише журналює повідомлення, не кидає exception. Task.handleRunning після ReleaseResource бачить ResourceAcquired=false й завершується з OriginalStopReason. Якщо він був WORK_DONE, FinalStopReason також лишається WORK_DONE попри close error. Це **не автоматично дефект**: можливий навмисний контракт best-effort cleanup, де close failure є лише діагностикою. Якщо ж контракт вимагає failure у FinalStopReason, первинна частина про успішний stop reason ще не усунута.

Уточнення власника 2026-10-02: задуманий контракт — закрити handle по можливості, а за close failure записати повідомлення в лог. Cleanup не повинен замінювати результат основної файлової операції. За цим контрактом вимога встановлювати FAILURE у FinalStopReason була зайвим припущенням агента; OF-006 закрито. Це не підтверджує фізичне закриття handle за bError: скидання flag означає завершення керування ресурсом із боку framework. FB_exit не проходив runtime validation.

Невелика діагностична неточність у новій error-гілці :230: log source/topic названі `FileHandleResourceManager.AcquireResource` / `.AcquireResource.Done`, хоча це ReleaseResource failure; також у повідомленні немає nErrId. Це не причина вважати close success, але ускладнює локалізацію failure.
