# OpenFramework: контекст для наступних сесій

## Постійні правила власника — 2026-10-06

Ці правила застосовуються до всього проєкту, включно з тестами й прикладами.
Нижчі датовані записи описують історію; старі плани не є дозволом виконувати
їх знову. Нові прямі уточнення власника мають перевагу над попередніми домовленостями.

### Документація біля декларацій

- Кожен новий тип (FB/клас, interface, DUT: enum, struct, alias тощо)
  повинен мати змістовний DocGen-коментар біля декларації.
- При зміні наявного типу актуалізуй його DocGen-опис; якщо опису немає,
  додай його в межах цього типу. Так само документуй нові або змінені методи,
  властивості й функції відповідно до їхнього призначення та контракту.
- Формат: `(*! ... *)` або `//!`, теги `<summary>`, `<description>`, `<param>`.
  Не змішуй XML DocGen з Markdown/rST. Зразок і деталі:
  `docs/audit/docgen-migration.md`.
- Summary пояснює призначення своїми словами. Description описує суттєві
  передумови, результати, зміни стану, ownership/lifetime, помилки й обмеження
  успадкування/callbacks, коли це стосується типу. Не додавай порожніх секцій
  і переказу очевидного синтаксису. Непогоджені припущення не видавай за контракт.
- Уточнення 2026-10-24: для констант із неочевидним призначенням пояснюй
  зміст і практичне застосування зрозумілими словами. Для бітових масок
  описуй, які біти вони виділяють або прибирають, до якого представлення
  застосовуються та як використовується результат; самої назви формату
  чи переказу імені константи недостатньо.
- Пояснення алгоритму всередині implementation залишай звичайними ST-коментарями.
  Ліцензійний notice також звичайний коментар; актуальна ліцензія — MIT,
  джерело `LICENSE.txt`. Зберігай авторство.

### Стиль Structured Text

- Уточнення 2026-10-20: якщо умова IF займає кілька рядків, THEN розміщуй
  на окремому рядку з тим самим відступом, що й IF.

- Уточнення 2026-10-19: у порівняннях із межами та спеціальними значеннями
  використовуй константи відповідних типів фреймворка (цілі числа, Reals,
  LongReals, дати, час тощо), а не дублюй їх літералами. Якщо потрібної
  константи немає, додай її до відповідного типу з описом призначення.

- Один оператор на рядок. IF/ELSIF/ELSE/END_IF, цикли, CASE і TRY/CATCH
  оформлюй багаторядково, навіть для одного RETURN або виклику.
- Приватні поля класів/FB починай з `_`. Це правило не переноситься автоматично
  на локальні змінні методів і параметри. Не перейменовуй сторонній API.
- Відділяй порожнім рядком логічно незалежні групи змінних та кроки алгоритму.
  Тісно пов'язані декларації й операції групуй разом; не вставляй механічно
  порожній рядок після кожної змінної чи оператора.
- Відступи, регістр і решту оформлення відтворюй за послідовними зразками
  власника в сусідньому коді. Стислі конструкції, раніше додані агентом,
  не вважай еталоном стилю.
- Якщо правило не описано і зразки не дають однозначної відповіді, запитай
  власника; не вводь власний стандарт без погодження.

Бажаний вигляд навіть для короткої умови:

```structuredtext
IF condition THEN
	CallMethod();
END_IF
```

### Контракт методів Try — 2026-10-20

- За прямим уточненням власника всі методи з префіксом Try не повинні
  викидати виключення назовні, зокрема пропускати їх із вкладених викликів.
  Правило діє в усьому проєкті, для публічних і приватних методів,
  незалежно від регістру написання префікса.
- Це цільовий контракт, а не твердження, що всі наявні реалізації вже
  відповідають йому. Перевіряти також залежності, callbacks, виділення
  пам'яті та стан/ownership після невдачі; самого CATCH недостатньо,
  якщо він залишає ресурси або стан некоректними.
- Погоджено для terminal OOM: Try повертає невдачу, а прапорець критичної
  нестачі пам'яті залишається встановленим. RaiseIfAllocationFailed
  піднімає помилку на межі задачі поза Try та recoverable handlers.
  Не скидати terminal flag і не перетворювати OOM на дозвіл продовжувати
  наступні цикли. Задачі без AutomationRunner також потребують цієї межі.

### Спеціальні lifecycle-методи — 2026-10-20

- Уточнення 2026-10-24: FB_init не підтримує значень параметрів за
  замовчуванням. Не задавай їх у декларації; у кожному місці ініціалізації
  явно передавай усі додаткові параметри FB_init, включно з нульовими
  посиланнями на необов’язкові залежності.

- За прямим правилом власника у FB_init, FB_exit та FB_reinit заборонено
  створювати й піднімати виключення. Це також стосується викликаних ними
  helpers: не використовувати throwing paths як штатну обробку відмови.
  Спеціальні lifecycle-методи мають завершуватися без exceptions.
- Якщо FB_exit порушив контракт під час TryRelease, helper повертає FALSE
  та обнуляє переданий pointer/interface. Це не гарантує завершення
  звільнення і не обнуляє інші aliases; частково зруйнований об'єкт не
  можна використовувати чи повторно видаляти через інші посилання.

- Уточнення 2026-10-21: для exceptions замість автоматичного реєстратора
  у FB_init використовується явна реєстрація в Clone після __NEW/null guard,
  до копіювання payload. Попередній компроміс із відкладеним registrar OOM
  скасовано. Plain __NEW не передає ownership менеджеру. Custom Clone
  зобов'язаний явно передати новий exception через
  DynamicMemoryManager.RegisterAutoDisposedObject поза lifecycle-методами.

### Простота та уточнення

- Уточнення 2026-10-23: не піднімати exceptions для штатної відсутності
  елемента, якщо контракт операції допускає такий результат. Зокрема,
  видалення за значенням, якого немає, може бути no-op, включно з порожньою
  колекцією; конкретну поведінку фіксувати біля API. Це не скасовує перевірок
  некоректних аргументів, обов'язкових передумов або terminal OOM і не є
  дозволом масово змінювати вже погоджені контракти інших методів.

- Зберігай режим TwinCAT Referenced Library при редагуванні проєктів.
  Квадратні дужки навколо назви бібліотеки в Resolution/DefaultResolution
  позначають посилання на PLC-проєкт; це не декоративне форматування.
  Не прибирай їх, не нормалізуй library identity і не змінюй VirtualLibrary,
  PlaceholderReference чи PlaceholderResolution без відповідного доручення.
  Редагуй .plcproj точково, без повторної серіалізації всього XML.

- Уточнення 2026-10-16: міграція діагностичних рядків з VAR_INPUT на
  VAR_IN_OUT CONSTANT стосується лише рядків довших за 255 символів.
  STRING(255)/WSTRING(255) у межах цієї міграції залишаються VAR_INPUT;
  це не вимога змінювати API, які вже раніше передавали рядки за посиланням.

- Обирай найпростіший зрозумілий людині код, який забезпечує погоджений контракт.
  Не додавай абстракцій, helpers, flags, fallback paths або TRY/CATCH лише
  «про всяк випадок». Кожне ускладнення повинно мати конкретну необхідність.
- Не приховуй реальних проблем заради меншої кількості рядків. Пояснюй
  необхідність складнішого рішення, його ціну та вплив на сумісність.
- У всіх випадках незрозумілого задуму, контракту, поведінки або стилю спочатку
  постав конкретне питання. Не вигадуй вимоги й не реалізуй непогоджене припущення.
  Залежну частину відклади до відповіді; незалежну погоджену роботу продовжуй.
- Не перепитуй вже погоджене. Працюй невеликими завершеними кроками; не розширюй
  локальний запит до масового рефакторингу чи форматування без доручення.
- Уточнення 2026-10-15: після погодженої правки автоматично переходь до аналізу
  наступної проблеми або групи поточного плану, не чекаючи команди «далі».
  Це не скасовує окремого погодження нових змін поведінки та уточнення контрактів.
- Нові явно підтверджені загальні правила записуй сюди, а рішення щодо конкретних
  контрактів — біля декларацій і в робочому журналі. Не записуй власну здогадку
  як правило власника.

### Ощадна робота з контекстом — 2026-10-22

- Для поточного кроку читай релевантні розділи документації та методи.
  Спочатку знаходь потрібні місця пошуком; не виводь великі файли цілком,
  якщо достатньо фрагментів. Розширюй читання, коли цього потребують залежності
  або розуміння контракту; економія токенів не виправдовує неповного аналізу.
- Не перечитуй уже доступний актуальний матеріал без потреби. Повторне читання
  потрібне, якщо контекст втрачено, файл міг змінитися або треба звірити точний
  код перед правкою. Обов'язкові інструкції та матеріали аудиту не пропускай.
- У робочому журналі стисло підтримуй поточний крок, погоджені рішення,
  внесені зміни, відкриті питання, статус перевірок і наступну дію.
  Не дублюй повну історію обговорення в кількох документах чи звітах.
- Звітуй стисло: результат, суттєвий вплив на сумісність, що не перевірено
  та яке рішення потрібне від власника. Фрагменти коду показуй для конкретної
  проблеми або вибору, без повторного виведення вже поясненого коду.
- Погоджені рішення повторно відкривай лише за новими фактами або дорученням
  власника; пояснюй, що саме змінило попередній висновок.
- Для переходу в новий чат використовуй збережений план і тематичний журнал
  як передачу стану. Новий чат не означає повторний аудит завершених кроків.
  Не вимагай нового чату після кожного кроку й не зупиняй дозволене продовження
  лише заради скорочення контексту.

### Поточна домовленість про перевірки

Власник сам виконує перевірки. Без нового доручення не запускай compilation,
TcUnit/runtime, XML validation, check-скрипти або генерацію DocGen.
Читання й пошук, необхідні для розуміння та редагування, дозволені.
У звіті точно зазначай, що змінено і що ще не перевірено. Старі записи про
виконані перевірки не підтверджують нову редакцію коду.

## Продовження роботи

Перед архітектурними змінами прочитай docs/audit/architecture.md.
Для продовження аудиту: docs/audit/README.md, findings.md, validation.md
і відповідний тематичний підсумок core-contracts.md, tasks-contracts.md
або exceptions-status.md. Контракти біля декларацій звіряй із поточним кодом.
Зберігай зміни власника; старі file/line references перевіряй заново.

Великий Task-план T00–T10 відкочений. Його попередня авторизація не чинна;
не відновлюй старий API, scripts чи tests. Погоджені поступові зміни після
відкату записані в tasks-contracts.md. Нові зміни поведінки погоджувати окремо.

TwinCAT sources — XML із CDATA; зберігай структуру й object IDs. Фактичне
library resolution не тотожне поточним sources. Не активуй target/hardware
для читання чи аудиту. XML parsing не означає ST compilation.

підсумків. Застарілі звіти, migration/check scripts і CompiledLibraries/audit
